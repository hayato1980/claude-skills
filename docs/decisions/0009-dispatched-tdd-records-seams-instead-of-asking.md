# 0009: 払い出された tdd は、シームをオーナーと合意せず、issue に記録して進む

## 決めたこと

- **`create-ccw-session` が払い出した修正側（対象ブランチ `claude/issue-<番号>` で `mattpocock-skills:tdd` を実行するセッション）は、シームを自分で決める。** 上流 `tdd` の「テストを書く前にシームをユーザーと合意する」は、この判断で置き換える。修正側は AskUserQuestion を出さず、返事も待たない。
- **最初のテストを書く前に、決めたシームを issue へコメントで残す。** 見出しは `## シーム` に固定する。シームごとに、何を捉え・何を捉えないか、根拠にした基準文書、検討してやめた案を書く。PR 本文には写さず、コメントへのリンクだけを置く。
- **シームを決める前に、レビュー側が Standards に使う基準を読む。** プラグインの `review-dialogue/standards.md` と、対象リポでコードの書き方を定めた文書（上流 `code-review` が Standards の基準として探すもの）。
- **払い出しの承認表では、シームを合意しない。** 止める機会は issue コメントで足りる。止めたいときは、オーナーがそのセッションへ直接メッセージを送る。修正側はコメントを監視しない。
- **手順の本文は `create-ccw-session` の「払い出された tdd のシーム」の 1 か所に置く。** 修正側はこのスキルを発動しないので、プラグインの hook `tdd-seam-policy.sh` が、`tdd` を発動した直後にその節と `standards.md` の絶対パスを差し込む。発火は対象ブランチのときだけ。

## なぜか

払い出された修正側の会話には、合意する相手がいない。利用先で同じ週に 3 本の `tdd` がこの点で迷った。

- 自分で決めて進めたが、根拠が会話にしか残らなかった。
- レビュー基準（[0007](./0007-tests-do-not-read-file-contents-with-regex.md)）に反するシームを選び、review-dialogue で差し戻されて往復が 1 回増えた。
- 最初のターンで合意を求める質問を出し、オーナーが気づくまで何時間も止まった。

返事を待つ案（issue で問う、承認表で合意する）は、3 本目と同じ止まり方をするか、払い出しのたびにオーナーが設計を読む手間を足す。記録して進めば、止まらず、根拠が会話の外に残り、オーナーは後からでも止められる。

## 範囲

- 対象は `tdd` のシーム合意だけ。ほかの上流スキルが持つ「ユーザーに確認する」手順は、事例がそろってから別に決める。
- 直接作業のセッション（ブランチ名が乱数）は対象外。オーナーが会話にいるので、上流のとおり合意する。
