# 0003: 指摘は、上流 code-review を包むスキル経由で 1 件 1 スレッドに着地させる

## 背景

上流の `mattpocock-skills:code-review` は差分を読んで Standards / Spec の所見を会話に返すだけで、GitHub も PR も
「指摘ごとに resolve できるスレッドが要る」という要件も知らない。runbook に書くだけでは、指摘が PR 本体コメント 1 本に
まとめて投稿され（resolve できず合意判定に載らない）、文章で縛る道は既に尽きていた。真因は上流の不足ではなく、
**上流の出力と PR の間の層が無いこと**。

## 決めたこと

1. **上流を包むスキル `review-dialogue` を置き、フロー語をこれにする。** 上流の名前をシャドウしない。
2. **器が merge-base を確定してから上流を呼ぶ。** 上流の "ask the user" 分岐に一度も入らせない。
3. **上流は Skill ツールで呼び、手順をコピーしない。** コピーは上流が更新されても静かに旧版のまま走る。
4. **所見は投稿より先に `.scratch/review-issue-<番号>.md` へ 1 指摘 1 項目で書き出す。** 書き出しを投稿の完了条件にし、
   投稿が途中で失敗しても続きから投稿し直せるようにする。
5. **機械化するのは指摘の投稿だけ。** 返信・resolve・ready 化は runbook のままにする（壊れていたのは投稿だけ）。
6. **修正側は PR を作ったら必ず自己チェックインを張り、ラダーを使い切っても指摘スレッドが 0 なら人へ渡す。**

## 採らなかった案

- スクリプトで投稿する（構造化データを書き、スクリプトが API を叩く）: 所見の構造化が難所で、スクリプトに移しても
  そこは変わらない。
- runbook の書き方を強める: 規約を引用したうえで禁じたチャネルに投稿する実例があり、指示は届いていた。
