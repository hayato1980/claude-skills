# 0006: 設定・IaC のテストは、ツール自身に評価させた値で確かめる

## 決めたこと

- **設定・IaC のテストは、ソースを正規表現・awk・grep で読まない。そのツール自身に評価させた値で確かめる。** IaC ツールの対話評価やプラン出力から、局所値・テンプレートの展開結果を JSON として取り出して読む。埋め込みのスクリプトは別ファイルに出し、テストから直接読み込む。
- なぜか: ソースの書き方（1 行の文字列がヒアドキュメントになる、関数の中で組み立てる、補間で値が入る）が変わるだけで、検査は空振りするか切り出せずに落ちる。確かめているのが「ソースにこう書いてあるか」であって、ツールが実際に組み立てる値ではない。切り出しを各テストが別実装で持つと、条件も食い違っていく。

## 評価できない形なら、テストより先にコードを分ける

評価したい値がリソースやデータソースを参照していて、プロバイダ無しでは評価できないときは、テストを曲げずにコードを分ける。純粋な局所値・テンプレートに切り出し、外の参照は引数で渡す形にする。

## 既存のテストは、触るときに移す

一度に直さない。**新しく書くテストからは禁止する。** 既存のテストは、そのテストか対象のコードに手を入れるときに移す。

## 限界

オフラインのテストが守れるのは**知っている規則**だけである。クラウド側の入力検査（例: 文書の作成 API が何を拒否するか）を見つける役には立たない。その規則は一次情報で調べ、テストに書き足す。

## レビューでの効かせ方

上流の `tdd` は書き換えられないので、規則を効かせるのはレビュー側になる。`review-dialogue` は上流 `code-review` に基準文書（[`standards.md`](../../plugins/dev-workflow/skills/review-dialogue/standards.md)）を Standards の基準として渡し、ソースを正規表現で読むテストを Standards の指摘に挙げる。
