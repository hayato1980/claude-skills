# 0001: レビューは実装と別セッション・別モデルで行う

## 背景

CI の自動 code review を置かない構成では、レビューは対話セッション側の 1 本だけになる。実装したセッションが
自分で `/code-review` を回すと、差分を読むのが同じコンテキスト・同じモデルになり、**第三者性が構造的に無い**。
さらに、安いモデルで実装を払い出すと、唯一のレビューまでそのモデルで走ってしまう。

## 決めたこと

1. **払い出しはフロー指定を必須にする。** フローを先に確定し、そのフローのモデルで子を起動する。
   フロー語が無ければ親が案を出し、オーナーが承認表で OK するまで払い出さない。
2. **指定語はフロー語（スキル名）のみ。** モデル名の直指定は受け付けない（割り当て表の劣化に気づけなくなるため）。
3. **モデルは既定 opus ＋ 例外表。** 例外表は [0005](./0005-model-follows-whether-errors-surface-immediately.md)。
4. **払い出された実装セッションは自分で `/code-review` を回さない。** 先に安いモデルの自己レビューが走り、
   その指摘を反映した状態で commit されると、「レビューは opus」が半分しか効かない。
5. **これを hook では止めない。** 同じリポジトリの hook をレビュー用の子も読むので、レビューのために払い出した子まで止まる。
6. **レビューは `review-dialogue` フローで別セッションに払い出す（opus）。** `source_revision` と `outcome_branch` に
   実装ブランチを渡す。レビュー側は push せず、指摘は PR 上のスレッドで投稿する。**直すのは修正側**で、全スレッドが
   resolved になるまで往復する。resolve とマージはレビュー側の専権（修正側が自分で閉じられると、レビュー側の確認を
   通らずに合意が成立してしまうため）。
7. **差分の基準点は毎回 merge-base。** 「前回レビュー以降」は追わない（前回どこまで読んだかはリポジトリのどこにも
   書かれていない）。
8. **`tdd` で始まったセッションに限り、レビュー払い出しを実装セッション自身が行う。** 禁止しているのは自己レビュー
   （`/review-dialogue` を自分の会話内で実行すること）であって、レビューを行う別セッションを起動することは別の操作。
   hook（`tdd-review-dispatch`）が PR 作成直後にこれを思い出させる。
9. **オーナーマージ対象（`needs-owner-merge`）は、基準表の行と差分の該当箇所を名指しできるときだけ付ける。**
   「迷ったら付ける」にすると、付けすぎでオーナーの手が常に要る運用に落ちる。基準表はリポ固有なので
   `docs/agents/review-dialogue.md` に置く。

## 結果

実装は安いモデル、レビューは別セッションの opus、という分担が成立する。代償は、往復のためにセッションが 2 本走ること。
