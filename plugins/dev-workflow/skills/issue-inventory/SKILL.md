このスキルは tracker への書き込み（ラベル変更・コメント・クローズ・`deferred` の作成）を確認なしで行える（`allowed-tools`）。許可の歯止めは手順 7 の**まとめて 1 回の承認**にある —— 承認前に書き込まない。

Use this skill when: open な issue が多く溜まり、どれから着手すべきかが一目で分からなくなったとき。判断は人が下す前提で、このスキルは**材料を揃えて提案するだけ**。

**`/triage` ではない。** `/triage` は自分が作っていない issue（外部からのバグ報告・要望）を agent-ready にするための入口。このスキルは既に agent-ready（またはそれに近い）open issue の**山**から、次の数件を選び出す出口側の作業。

## 発動トリガー

- 「issue を棚卸して」「issue の棚卸し」
- 「次に何を着手すべきか」「次に払い出す issue を選びたい」
- 「open issue を整理したい」
- スラッシュコマンド `/issue-inventory`（プラグイン名つきの正式名は `/dev-workflow:issue-inventory`）

---

## 手順

### 1. tracker を決める

**tracker（どのリポジトリの課題か）**: 対象リポジトリに `docs/agents/issue-tracker.md` があればそれに従う。無ければ `git remote -v` から決める。どちらからも決まらなければユーザーに tracker を聞いて停止する（推測で進めない）。

**操作手段（GitHub の場合）**: `issue-tracker.md` の有無や記述に関係なく、実行環境で決める。`command -v gh` で `gh` CLI があれば `gh`、無ければ GitHub MCP ツール（`mcp__github__*`）を使う（クラウドの実行環境には `gh` が無いことが多い）。どちらも使えなければユーザーに伝えて停止する。以降の手順の「ラベル取得操作」などは、ここで決めた手段で行う。

対象リポジトリに `docs/agents/triage-labels.md` があれば、ここで一緒に読む。手順 3・4・7 の**リポジトリ固有の扱い**（棚卸しで除外するラベル、払い出せないラベル、評価の補正）はそこに書かれている。

### 2. ラベルの存在を確認する

`deferred` と `duplicate` を、tracker のラベル取得操作で確認する。

- 両方あれば通常モードで進む。
- `deferred` が無ければ「ラベル無しモード」に落ちる。今回の棚卸しはラベル無しモードのまま最後まで進める（停止しない）。
  - 手順 1 で決めた操作手段にラベル作成の手段がある（`gh` が使える、またはこのセッションの MCP にラベル作成ツールがある）なら、`deferred` の作成を手順 7 の書き込み提案に含める（承認後に実行する。ここでは作らない）。
  - 無ければ、出力の末尾に「`deferred` ラベルが無いため見送り判断はラベルに残せません。オーナーに作成を依頼してください」と 1 行添える。
- `duplicate` が無い場合も同様に 1 行案内して続行する（GitHub ではデフォルトで存在するため、通常は起きない）。

### 3. open 全件を浅く取る

タイトル・ラベル・更新日時・assignee のみを取得する。**本文は読まない。**

次のラベルが付いたものは候補母集団から除外し、ラベルごとに件数だけ数えておく（手順 7 の出力で使う）。

- `deferred`（前回の棚卸しで「今はやらない」と判断済み）
- `docs/agents/triage-labels.md` が「棚卸しで除外する」と定めたラベル（例: 外部の上流待ち）

`docs/agents/triage-labels.md` が「子セッションへ払い出せない」と定めたラベル（例: `ready-for-human`）は**除外しない**。人が着手すれば進むので候補に挙げてよいが、手順 7 の `/create-ccw-session` 行は付けない。

### 4. 2 軸で評価して 5〜8 件に粗選びする

タイトルとラベルだけから、下表の 2 軸で当たりを付ける。**緊急×重要が最優先**。

| 軸 | 上げる信号 |
|---|---|
| **緊急度** | 本番・運用経路が止まる／数字が誤る（意思決定に使う指標に影響）／CI が赤で全 PR がブロックされる／セキュリティ／放置すると被害が広がる（誤ったデータが蓄積する等） |
| **重要度** | 下流の issue を複数アンブロックする／繰り返し発生するコストを消す／重複実装を 1 本に畳む／それ自体が他の判断の前提になる |

「どこが運用経路か」は**対象リポジトリ自身のドキュメントから読む**（`CLAUDE.md` / `AGENTS.md` のエントリポイント・運用手順の記述など）。repo 固有の知識をこのスキル本文に焼き付けない。`docs/agents/triage-labels.md` に評価の補正（例:「このリポジトリでは CI 赤は全 PR を止めないので緊急度を上げない」）があれば、上表より優先する。

粗選びは 5〜8 件程度に絞る。全件の本文を読むのはこの先の手順 5 だけにする。

### 5. 粗選びした数件だけ本文を深く読む

粗選びした issue の本文を読み、本文中の `#NNN` 参照を辿ってブロッカーの有無を確認する。`Blocked by: #NNN` の規約行があればそれを最優先で拾い、無ければ「#729 から分離」「#779 の未了分」のような散文中の参照から文脈で判断する。open なブロッカーを持つものは候補から外すか、依存ありと注記する。

次に、粗選びした各 issue（**5〜8 件だけ**）について、実装済みで閉じ忘れていないかを main のコミットで確かめる。事前に `git fetch origin main` を流し、各 issue について `git log origin/main --oneline -E --grep='#<番号>([^0-9]|$)'` を実行する（右側の境界が無いと `#195` が `#1958` にもヒットする）。issue を閉じる記述（`Closes #NNN` 等）の無い PR で実装された場合、tracker 上の紐づけからは見えないため、コミットを直接確かめる。

- ヒットがあれば、コミットの内容を issue 本文の完了条件と突き合わせる。満たしていれば候補から外し、手順 7 の書き込み提案に「close（completed）＋根拠のコミット」として回す。
- 一部だけ済んでいる場合は、残りが何かを候補の行に注記する。
- `git` が使えない（リポジトリ内でない・`origin` や `origin/main` が無い等）ときはこの確認を飛ばし、出力に「main のコミット確認を飛ばしました」と 1 行添える（停止しない）。

残った候補を**領域が被らないよう散らして** 3〜5 件に絞る。同じ領域（例: 同じディレクトリ配下）の issue を複数同時に候補へ並べない。候補の段階で領域が被っていると、後で `/create-ccw-session` などで同時に払い出したときに 2 つの子セッションが同じファイルを別々に直して衝突しうる。

### 6. 陳腐化・重複を拾う

手順 3 で取った全件のうち、次の **2 つの信号だけ**で深く読む対象を絞る。

- 最終更新から 30 日超
- タイトルが closed issue / merged PR と重なる

この 2 つ以外（例: 「関連 issue の兄弟が軒並み closed」「コメント 0 のまま古い」）は信号として使わない。誤検出が多く、まだ着手していないだけの issue を陳腐化と誤判定してしまう。

対象を深く読み、重複と判断したものは既存の `duplicate` ラベル + 統合先へのコメント案を、見送りと判断したものは `deferred` ラベル + 理由コメント案を用意する（実際の書き込みは手順 7 の承認後）。

### 7. 出力する

次の 2 セクションで出力し、**まとめて 1 回**ユーザーに承認を求める。承認されたぶんだけ、tracker への書き込み（ラベル変更・コメント・クローズ）を実行する。承認前に書き込みをしない。tracker へ書くコメントの署名・定型（attribution footer 等）は `docs/agents/issue-tracker.md` に従い、無ければ実行環境の既定の署名に従う。

```
## 1. 次の候補（3〜5 件）
   番号・タイトル・緊急度と重要度の置き方（各 1 行）・依存の有無
   末尾: /create-ccw-session #NNN   ← そのスキルが在る repo でのみ。払い出せないラベルの issue には付けない

## 2. 書き込み提案（承認後まとめて実行）
   close / duplicate + 統合先コメント / deferred + 理由コメント / ラベル修正
   末尾: 現在 deferred が N 件（手順 3 で除外した他のラベルも同様に件数を出す）
```

## この設計の理由

- **順位付けをしない。** 2 軸で候補を絞り、根拠を添えて人が選ぶ。機械的スコアリングは「どれが重要か」というプロジェクトの方針そのものに数値の皮を被せるだけで、もっともらしく間違えるぶんかえって有害。
- **コードは開かない。** 全件のコード確認は 1 回の実行が現実的な時間に収まらない。現物確認は着手した子セッションの仕事。手順 5 の `git log origin/main --grep` はこの方針に反しない: コードを開く作業ではなくコミットメッセージの照会で、対象も粗選び後の 5〜8 件に絞っているため、1 回の実行時間に収まる。
- **陳腐化の信号を 2 つに絞る。** 関連 issue の連鎖や「コメント 0」は誤検出が多すぎる。
- **書き込みはまとめて 1 回承認。** close だけ都度承認・ラベルは自動、のような非対称にすると線引きの判定コストが毎回発生し、一番取り返しがつかない close で間違えやすい。
- **出力は揮発させ、台帳を作らない。** 別の場所に一覧を書くと、その一覧と issue の実態を同期する仕事が新たに発生し、誰もやらなくなって腐る。判断は issue 自身にラベルとコメントで残す。
- **見送りは `deferred` ラベル（自動復活しない）。** コメントのみだと手順 3 の浅い舐めでは見えず、次回また同じ issue を候補に挙げてしまう。`wontfix` は「対応しない」であり「今はやらない」より強く意味が違うため流用しない。N 日での自動復活もしない（見送った理由が解決していないのに戻ってきて、また見送るだけになる）。
- **優先度ラベル（`P0`〜`P2` 等）は導入しない。** 緊急度は時間とともに変わる（例: CI が直れば緊急度は消える）ため、固定ラベルは同じように腐る。毎回その場で評価する。
- **払い出しは繋がない。** 打てる形のコマンド行を添えるだけで、内部から `/create-ccw-session` を呼ばない。承認が 2 種類になるうえ、誤った払い出しは後始末（`archive_session` 等）が要る。
- **repo 非依存。** tracker もラベルも実行時に発見し、無ければ劣化して動く（ラベル無しモードなど）。このスキル本文は特定の issue 番号や `[meta]` のような命名規約に依存しない。共有プラグイン `dev-workflow` として配るので、各 repo はコピーしない。導入はユーザー設定か、クラウド環境の Setup script で行う（リポの `.claude/settings.json` では有効化されない。配布元の README を参照）。
