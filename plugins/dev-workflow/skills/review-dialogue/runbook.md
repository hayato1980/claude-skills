# レビュー往復（修正側 ↔ レビュー側）

払い出された `review-dialogue` セッションと、その PR を作ったセッションが、**PR 上のスレッドで合意に至るまで往復する**手順。**修正側とレビュー側の両方がこの 1 文書を読む**（作法が割れると往復が噛み合わないため、正準はここ 1 箇所に置く）。

判断の記録は [判断 0001](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0001-review-runs-in-a-separate-session-and-model.md)・[0002](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0002-review-rounds-wake-the-counterpart-directly.md)・[0003](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0003-findings-land-through-a-wrapper-skill.md)、払い出しの手順は [`create-ccw-session`](../create-ccw-session/SKILL.md)。

**リポ固有の設定は、対象リポの `docs/agents/review-dialogue.md` が持つ**（オーナーマージの基準表・CI が走る条件・push 前に流すコマンド）。本文書はその見出しを実行時に読む。無い・見出しが欠けているときは、推測せず、該当の手順に進む前に止まってユーザーに聞く。

---

## 役割

**修正側**: その PR を作ったセッション。払い出された `tdd` の子でも、このリポジトリで直接作業しているセッションでも、`diagnosing-bugs` の子でもよい。**役割はセッションの出自ではなく PR に対する立場に宿る。**

**レビュー側**: `review-dialogue` フローで払い出された子（opus）。上流 `mattpocock-skills:code-review` を包み、指摘を本文書の作法で PR スレッドへ着地させる（→ [`SKILL.md`](./SKILL.md)）。

往復が始まる条件は **レビューが払い出されたこと**であって、PR の作者が誰かではない。レビュー側は差分を読む前に作者を調べなくてよい。

---

## 全体の流れ

```
レビュー側  指摘をスレッドで投稿 → ラウンドを閉じる
                  ↓ ポークで起床（1〜2 分）
修正側      直して push、または反論 → スレッドに返信 → ラウンドを閉じる
            （CI 赤・コンフリクトは通知で自分で起きて直す。ただし PR が ready の間は push せず、draft に戻ってから。基盤の問題なら 1 回だけ回し直し、base 起因で main に修正が無ければ人へ）
                  ↓ ポークで起床（1〜2 分）
レビュー側  取り下げ or 維持を明示 → 納得したスレッドを resolve
                  ↓
            全件 resolved → ready_wait_merge.sh で CI 待ち → green ならマージ → 修正側をポーク → 購読解除 → 終了
                            （needs-owner-merge なら --no-merge で ready 化して CI を見届けて止める / CI 赤・コンフリクトなら draft に戻して往復へ。直すのは修正側）
            割れたまま 3 往復 → 決裂として人へ渡す → 購読解除 → 終了
            相手が来ない      → 打ち切りとして人へ渡す → 購読解除 → 終了
            表に無い中身の判断が要る → オーナー判断待ちとして人へ渡す → 購読解除 → 終了（判断後はレビューを払い出し直す）
                  ↓ マージ後、ポーク（オーナーマージなら merged イベント）で起床
修正側      retro-closeout（retro → 承認表 → 着地 → レビュー側と自分をアーカイブ）
```

## ラウンドの閉じ方（両側共通）

**自分の番を終えるたびに、この 4 手を行ってからターンを終える。** 両側が同じ手順を踏む
（→ [判断 0002](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0002-review-rounds-wake-the-counterpart-directly.md)）。

### 1. 相手を引く

**判定はスクリプトが持つ。** 候補の絞り込み・自分の除外・向き・曖昧なときの拒否は `scripts/ci/session_closeout.sh counterpart` の 1 か所だけにあり（→ [判断 0008](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0008-counterpart-rule-lives-in-one-script.md)）、この文書にも他のスキルにも写さない。MCP を呼んで結果ファイルを渡す手順だけが prose に残る。

1. 一覧を取る。結果は大きく、ツールが**ファイルに保存する**ので、保存されたパスをそのまま使う（`limit` は API の上限 100）。

   ```
   mcp__claude-code-remote__list_sessions(mine=true, limit=100)
   ```

2. 呼ぶ。`--want` は**探す側**: 自分がレビュー側なら `fixer`、修正側なら `reviewer`。

   ```bash
   scripts/ci/session_closeout.sh counterpart --want <reviewer|fixer> --issue <番号> [--since <対象の作成時刻>] <list_sessions の保存ファイル（取得順）>... [--session <get_session の保存ファイル>]...
   ```

   対象ブランチは既定で `claude/issue-<番号>`。PR の head がそれと違うとき（オーナーの直接セッションが作った PR など）は `--head <PR の head ブランチ>` を足す。issue を持たない PR は `--issue` の代わりに `--pr <PR番号> --head <PR の head ブランチ>`。**`--since` は `--want reviewer` のときだけ渡す**（修正側は対象より前に作られうる —— issue を持たない PR では PR を作ったセッション自身で、直接作業なら issue より前にもいる。`fixer` に渡すと古い行で打ち切られ、後ろのページの修正側を `none` と誤判定してポークが空振りする）。`--since` には対象の issue（`issue_read`）、PR を対象にするなら PR（`pull_request_read`）の `created_at` をそのまま渡す。相手のセッションは対象より前には作られないので、読んだ最も古い行がこの時刻より前に届いた時点で、スクリプトは続きのページを読まずに判定する（アーカイブ済みが溜まったアカウントで、`none` を言い切るために何ページも読まされない → #59）。省略すると今までどおり最後のページまで読む（`--want fixer` ではこれが正しい）。レビュー側を引くときは必ず渡す。自分の除外は、スクリプトが環境変数 `CLAUDE_CODE_REMOTE_SESSION_ID` から行う（接頭辞の違い `cse_` / `session_` も吸収する）。`bash` を前置せず単独で呼ぶ（許可ルールが固定パスを指すため）。

3. 終了コードで次を決める。
   - **2** → ページが足りない。stderr の `after_id` で `list_sessions(mine=true, limit=100, after_id=…)` を引き、保存ファイルを**末尾に足して**呼び直す。アーカイブ済みだけのページが 2 枚続けば、スクリプトがそこで打ち切る（実測 → #31）。
   - **3** → `list_sessions` の行に `session_context` が無い（実測では常に無い → #30）。stderr の id を `get_session(session_id)` で引き、保存ファイルを `--session` で 1 つずつ足して呼び直す。**候補が 1 つでも必ず引く**（違う相手を起こしても手順上は成功に見えるため）。`get_session` の呼び出し自体が失敗した id は、呼び直さず「相手を引けなかった」として人へ渡す。`get_session` の結果がファイルに保存されず画面にそのまま返ってきたときは、その JSON をそのままファイルに書いて `--session` に渡してよい（`list_events` の結果と同じ扱い）。
   - **1** → 入力・読み取りの失敗。「相手を引けなかった」を明示して手順 3 へ進み、チェックインの中で人へ渡す。
   - **0** → 標準出力の 1 行で決める。
     - `found <session_id>` → それが相手。手順 2 へ。
     - `none` → 相手が引けない（正常系。レビューがまだ払い出されていない、修正側がオーナーの手元セッションで `issue-<番号>` タグを持たない）。手順 2 を飛ばして 3 へ進む。
     - `ambiguous <id>,<id>,…` → **どれも起こさない。** 同じ issue に押す子が 2 本走っている異常事態なので、ポークは撃たずに手順 3 へ進み、チェックインの中で人へ渡す。新しい順などで 1 本選んではいけない（間違った相手を起こしても手順上は成功に見える）。

**中継（`scripts/ci/session_closeout.sh`）が無い、または失敗するときも、黙って次へ進まない。** 「相手を引けなかった」を明示して手順 3 へ進み、人へ渡す。古い手順（`list_sessions` を `jq` で読む）へ戻らない —— 規則が 2 箇所にあると割れる。中継は各リポに置く（→ [README](https://github.com/hayato1980/claude-skills/blob/main/README.md)「各リポに置く中継スクリプト」）。

**やってはいけないこと**（スクリプトの判定は、これらを避けるように作ってある。変えるときは判断 0002 / 0008 を読む）:

- **`revision` を引く条件にしない。** 行に `session_context` が無いまま revision を必須条件にすると、修正側からレビュー側が 0 件に見えてポークが空振りし、往復が静かに止まる（#30）。revision は `get_session` で補ってから役割を決める。
- **役割判定を `tags` のフロー語で行わない。** 第 3 タグとフロー語が同じ文字列になりうる。引く条件は `issue-<番号>`（または `pr-<PR番号>`）タグと revision。
- **`RUNNING` に絞らない。** 待っている相手は `SESSION_STATUS_IDLE` で、往復の待ち時間のほとんどはこの状態にある。外すのはアーカイブ済みだけ。
- **`title` で突き合わせない。** 実データの title には打ち間違いが現にある。
- `list_sessions` の **`tags` 引数**は OAuth caller 専用で、子セッションからはエラーになる。サーバー側で絞る手段は無い。

#### list_events の保存ファイルの読み方

他セッションの会話を読むときの `list_events` は、`kinds=["assistant","result"]` に絞っても上限を超えてファイルに落ちる。スクリプトが保存ファイルから JSON 行を取り出す（行番号に頼らない）。assistant のテキストが時系列に並び、`result`（ターンの終わり方）は `[result <subtype> is_error=<真偽>] <最終テキスト>` の 1 行で出る：

```bash
scripts/ci/session_closeout.sh events <保存されたファイル>
```

結果がファイルに落ちずにそのまま返ってきたときは、その JSON を同じ条件で読めばよい。

### 2. 相手を起こす（ポーク）

```
mcp__claude-code-remote__create_trigger(
  name="[往復] PR #<PR 番号> → <相手の役割>",
  persistent_session_id="<手順 1 で引いた session_id>",
  run_once_at="<現在の UTC + 1 分、RFC3339>",
  initiation="own_followup",
  prompt="PR #<PR 番号> のレビュー往復で相手がラウンドを終えた。review-dialogue スキルの runbook の自分の手順を実行せよ。",
)
```

- **`run_once_at` は +1 分。** スケジューラは最大 60 秒遅れて発火するので、実効の遅延は 1〜2 分になる。
- **本文に指摘の要約を載せない。** 一次情報は PR にあり、相手は自分で読める。要約を載せると「ポーク本文」と「PR の実体」で情報源が 2 つになり、食い違ったときどちらが正か決まらない。載せるのは PR 番号だけ。
- 発火した Routine は `ended_reason: run_once_fired` で自動的に無効化される。**後始末は要らない。**
- **`fire_trigger` は使わない。** 実測で相手に届かない（→ [環境の前提](#環境の前提実測状況)）。

### 3. 自己チェックインを張り直す

```
mcp__claude-code-remote__delete_trigger(trigger_id="<前回張ったチェックイン>")
mcp__claude-code-remote__send_later(delay_minutes=<5 → 10 → 20 → 40>, message="...", name="...")
```

- **消してから張る。** 「待っているチェックインは常に 1 本」を保つ。消さないと古いものが残って起床が増え、**残り回数も数えられなくなる**。
- **ラダーは相手の沈黙が続いている間だけ進む。相手が返してきたら 5 に戻す。** これが無いと、往復が順調に 5 ラウンド続いただけで「4 回使い切った」に達してしまう —— 打ち切りは[相手が来ないとき](#相手が来ないとき)の判定であって、ラウンド数の上限ではない。
- 間隔は **5 → 10 → 20 → 40 分の 4 回（計 75 分）**。相手が黙っている理由は時間とともに変わる —— 最初の数分は「まだ差分を読んでいる」で待てば解決するが、30 分黙っているなら「テストが長い」か「セッションが消えた」で、5 分刻みで突いても解決しない。
- **張ったら、そのターンの最後の要約（`post_turn_summary` の `status_detail` に出る文）に、次に起きる UTC 時刻と、待っている相手（ポーク済みかどうか）を書く。** 待つ側は `IDLE`（`status_bucket` は `review_ready` / `working`）でターンを終えるので、外から見ると「正常に待っている」と「止まっている」が区別できない。時刻が書いてあれば、親やオーナーは「その時刻が過ぎるまでは待っているだけ」と読める。例: 「R2 の指摘待ち。ポーク済み。次のチェックイン 13:23 UTC」
- チェックインは**保証**であってポークの予備ではない。ポークは速さと空振りの少なさを買うだけで、**往復が人手なしで進むことを担保しているのはこちら**（→ [判断 0002](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0002-review-rounds-wake-the-counterpart-directly.md)）。

### 4. 購読してターンを終える

```
mcp__claude-code-remote__subscribe_pr_activity(owner, repo, pullNumber)
```

購読は**明示的に呼ぶ**。ハーネスの自動購読は「PR を作ったら」発火するので、PR を作っていないレビュー側は自動では購読されない。冪等なので毎ラウンド呼んでよい。呼んだかどうかは、自分の直前の発言（この手順の呼び出し）を振り返れば分かる —— 呼ばずに終えたことに気づいたら、次のラウンドのこの手順で呼び直せばよい（冪等なので取り返しがつく）。

**購読を飛ばしたときの安全策。** 呼んだかどうかを確かめる仕組みは無く、飛ばしたことに気づくのは終わり方（[合意](#7-合意--マージまで進める)・[決裂](#8-決裂--打ち切り--人へ渡す)）で確かめたときになりうる。起床を保証するのは購読ではなく[自己チェックイン](#3-自己チェックインを張り直す)なので、未購読でも往復は止まらないが、人が PR にコメントしたときに気づけなくなる。だから終わるときに、そもそも購読していたかを一度確かめる（7・8 の「購読を解除する」の前）。

**レビュー側が実装と同一セッション（自己レビュー）の場合は、そもそも運用の外にある。** 払い出された子は自分で `/code-review` を回さないので、自己レビューは正規の経路では起きない。それでも実際に自己レビューで走った場合は、手順 1（相手を引く）・手順 2（ポーク）は空振りする（`issue-<番号>` タグを持つ自分以外の非アーカイブ行が存在しない＝0 行）。この手順（購読）を呼ぶかどうかは自分で選べるが、呼んでおけば人のコメントに気づける可能性が増える。

## 相手が来ないとき

チェックインで起きたら、**自分が張ったポークの結末も見る**（どのみち起きているので追加コストはゼロ）。

```
mcp__claude-code-remote__list_triggers(include_completed=true)
```

| 見えたもの | 意味 | やること |
|---|---|---|
| `last_run.status: SUCCEEDED` | **配送された**（相手が動いたことまでは意味しない） | チェックインを張り直して待つ |
| `ended_reason: auto_disabled_session_gone` | **相手セッションが消えている**（消滅を名指ししている） | **即「打ち切り」** |
| `last_run.status: FAILED` で `ended_reason` が消滅を示さない | **配送に失敗した。理由は不明** —— 一時的でありうる | **もう 1 回ポークを撃ち、チェックインを張り直す。2 回続いたら打ち切り** |
| チェックインを 4 回使い切った | 相手は居るが応答しない | **「打ち切り」** |

相手が消えていると確定したら残りのチェックインは**確実に空振りする回数**でしかないので、75 分待たずに人へ渡す。

## レビュー側の手順

### 1. 差分を読んで指摘を作る

基準点は**毎回 merge-base**（→ [判断 0001](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0001-review-runs-in-a-separate-session-and-model.md)）。「前回レビュー以降」は追わない。

### 2. 指摘を 1 件 1 スレッドで投稿する

```
mcp__github__pull_request_review_write(method="create", ...)      # pending review を作る
mcp__github__add_comment_to_pending_review(...)                   # 指摘ごとに 1 回
mcp__github__pull_request_review_write(method="submit_pending", event="COMMENT", ...)
```

- **行に紐づく指摘**は `subjectType="LINE"`、**紐づかない指摘**は `subjectType="FILE"` で該当ファイルに寄せる。
- **PR 本体コメントを指摘に使わない。** resolve できないので合意判定に載らない。本体コメントはサマリと決裂報告の専用。
- どのファイルにも寄せられない指摘は、差分レビューの出力として粒度が粗すぎる。ファイルを名指しできる形まで具体化する。
- `event` は **`COMMENT` のみ**。`APPROVE` / `REQUEST_CHANGES` は GitHub が自分の PR への承認・変更要求を拒否するため使えない（修正側・レビュー側・PR 作者はすべて同一アカウント）。

### 3. 本文の先頭に役割マーカーを置く

```
[レビュー] <指摘本文>
[レビュー] R2/3 <2 往復目の返信>
```

**これは飾りではない。** 修正側と GitHub 上で同一アカウントなので投稿者名で役割を区別できず、マーカーが無いとハーネスの「自分のコメントのエコーは無視してよい」ルールにより、**相手の発言を自分のエコーと誤認して往復が止まる**。

### 4. ラウンドを閉じる

→ [ラウンドの閉じ方](#ラウンドの閉じ方両側共通)

### 5. 修正側の返信に応える

修正側の返信には必ず**「取り下げ」か「維持」を明示**する。どちらか伝わらないと修正側が次の行動を決められない。

- **取り下げる**: 修正側が**事実**を示したとき（テストが通る出力、該当コードが存在しない、仕様書の該当箇所）。これは反論ではなく事実訂正なので、正しければ取り下げる。
- **維持する**: 反論が判断の相違にとどまるとき。維持されたら修正側は従う。

`[レビュー] R2/3` の形で往復回数を本文に書いて残す。**カウントはスレッド単位**で、上限は 3 往復。1 つの論点が割れているだけで、合意済みの他の指摘まで止めない。

### 6. スレッドを resolve する

```
mcp__github__resolve_review_thread(owner, repo, threadId)   # threadId は PRRT_... の node ID
```

thread の node ID は `mcp__github__pull_request_read(method="get_review_comments")` が返す。**resolve はレビュー側の専権**（取り下げた指摘も含めて全件）。修正側は resolve しない —— 修正側が自分で閉じられると、レビュー側の確認を通らずに合意が成立してしまう。

### 7. 合意 —— マージまで進める

**全スレッドが resolved になったら合意。** 合意したら、レビュー側が**マージまで**進める。**マージに進めるのはレビュー側だけ**で、修正側には持たせない（第三者性を保つため）。例外は**オーナーマージ対象**（`needs-owner-merge` ラベル）だけで、そちらは ready 化して CI を見届け、止める。

**ready 化の前に、PR 本文が最終の差分と一致しているかを見る。** 食い違っていれば、**指摘スレッドとして投稿**し（PR 本体コメントにしない。[手順 2](#2-指摘を-1-件-1-スレッドで投稿する)）、直るまで resolve しない。直す責任は修正側（[修正側の手順 3](#3-指摘に応える)）。投稿したら[ラウンドを閉じ](#ラウンドの閉じ方両側共通)、全スレッドが resolved になったら本手順 7 をやり直す（同じターンで `mergeable_state` の確認や ready 化に進まない）。この確認は 7-1 より前にあるので、`needs-owner-merge` の経路でも行う。

**ready 化の前に、コンフリクトが無いかを見る。** `pull_request_read(method="get")` の `mergeable_state` が `dirty` なら ready にせず、draft のまま下の「CI が赤だったとき」と同じ手順で修正側へ返す（スレッドには「コンフリクト」と書く）。GitHub はコンフリクトを抱えた PR では `pull_request` 系の workflow を起動しないので、そのまま ready にすると `ready_wait_merge.sh` は check run を待ってタイムアウトするだけになる。`mergeable_state` は計算が遅れて `unknown` を返すことがあるので、そのときは数十秒おいて 1 回だけ取り直し、それでも `unknown` なら先へ進む（タイムアウト行で拾う）。

#### 7-1. オーナーマージ対象かを判定する

**マージに進む前に、毎回差分を見て判定する。** ラベルが既に付いていればそれに従う。付いていなくても、差分が対象リポの `docs/agents/review-dialogue.md` の `## オーナーマージの基準表` の**行に当たる**なら、**レビュー側が自分で `needs-owner-merge` を付けて**止まる。判定は**触ったファイルではなく、マージで本番の振る舞いや決定が変わるか**で行う。

- **付けるのは、基準表の当たった行と、差分の該当箇所を名指しできるときだけ。** 名指しできないなら付けない（「迷ったら付ける」はしない）。付けたら PR 本体に `[レビュー] needs-owner-merge を付けました: <該当した基準> / <差分の該当箇所>` と 1 行書く。
- **前例をたどって広げない。** 過去の PR に付いていたことは、この PR が表に当たる理由にならない。
- **基準表が無い・読めないときは、付けるかどうかを推測しない。** ユーザーに聞いて止まる。
- **ラベルの付与に失敗したら**（リポジトリにラベルが未作成。CCW からは作れない）、PR 本体に `[レビュー] needs-owner-merge 該当（ラベル未作成のため付与できず）: <該当した基準>` と書き、**ラベルが付いているものとして 7-2a へ進む**。
- **表に無い「オーナーの判断待ち」はこのラベルに乗せない。** issue が「意図した変化はオーナー判断」としている差分、受け入れ条件の未達、証拠を省いた据え置きなど、**中身の判断**が要るものは、マージの承認ではないので [8](#8-決裂--打ち切り--人へ渡す) と同じ形で人へ渡す（PR 本体に `[レビュー] オーナー判断待ち` として何を判断してほしいかを書き、`ready-for-human` を付け、**draft のまま**、購読を解除し保留中のチェックインを消して終わる）。**このレビュー側はそこで終わり、判断を待たない。** オーナーは PR 上で判断を返し、`ready-for-human` を外して `/create-ccw-session #<番号> review-dialogue` で**レビューを払い出し直す**（差分の基準点は毎回 merge-base なので、新しいレビュー側がそのまま続きを読める）。待つ側に購読を残さないのは、判断が数日かかることがあり、その間チェックインを張り続ける根拠が無いため。
- **ラベルは誰が付けてもよい**（起票側・修正側・レビュー側）が、どの役割でも同じ基準表で判定する。**外せるのはオーナーだけ**で、Claude はどの役割でも外さない。

#### 7-2a. オーナーマージ対象 —— ready 化し、CI を見届けて止める

```bash
scripts/ci/ready_wait_merge.sh --no-merge <PR番号>   # Bash の run_in_background で起動する。先頭に bash を付けない
```

ready 化 → CI 完了待ち → green でも**マージせずに止める**（終了コード 0。出力は「CI green。マージせずに止めます。」）。マージはオーナーが行う。マージ＝オーナーの承認として残すための例外である。7-2b と同じスクリプトなので、手元ゲート・HEAD 一致の確認・前の周の check run を取り違えない仕組みも通る。**起動の形（単独・先頭に `bash` を付けない・バックグラウンド）と、出力ごとの分岐は 7-2b の表と同じ**。ただし次の 3 点が違う。

- **`CI green。マージせずに止めます。`** → 購読を解除し、保留中のチェックインを消して終わる（`unsubscribe_pr_activity` / `delete_trigger`）。マージはオーナーを待つ。
- 7-2b の表の **`PR #N をマージしました。` の行（修正側への retro-closeout のポーク）と、マージ時の `405` の行・`409` の行は、`--no-merge` では起こらない**（マージを呼ばない）。それ以外の行（赤・タイムアウト・手元ゲート失敗・それ以外）は表どおり。赤なら**自分で draft に戻してから**往復に戻り、全スレッドが resolved になったら本手順 7 をやり直す。オーナーに赤い ready の PR を渡さない。
- **green の判定は、対象リポの `docs/agents/pr-merge-gate.md` の「CI で止めるジョブ」だけで行う。** 以前の 7-2a は PR の最新 head の check を全部見ていたので、止めるジョブ以外の check はこのスクリプトでは見ない。green で止めた後、オーナーがマージ前に他の check も見る。

#### 7-2b. それ以外 —— `ready_wait_merge.sh` でマージまで

```bash
scripts/ci/ready_wait_merge.sh <PR番号>   # Bash の run_in_background で起動する。先頭に bash を付けない
```

ready 化 → CI 完了待ち → green ならマージ、を 1 本で行う（→ [`ready-merge`](../ready-merge/SKILL.md)。止めるジョブ名は対象リポの `docs/agents/pr-merge-gate.md`）。**上の形のまま、1 回の Bash 呼び出しで単独に叩く。** 先頭に `bash` を付けたり、`git checkout` / `git pull` と `&&` でつないだりしない。`.claude/settings.json` の許可ルール `Bash(scripts/ci/ready_wait_merge.sh*)` に一致するのはこの形だけで、外れると auto mode の分類器に回り、`[Merge Without Review]` として拒否されうる。`bash …*` の形の許可ルールは「ワイルドカード付きのインタプリタ」とみなされ、auto mode に入った時点で無効になる。ブランチの準備が要るなら、その前に別の呼び出しで済ませる。**CI 待ちは最大 40 分**で、Bash の前面実行の上限（10 分）を超えるので**必ずバックグラウンドで起動し、終了通知で起きる**。結果は stdout / stderr の文言で分岐する（終了コードはどの失敗も 1）。

| 出力 | 意味 | やること |
|---|---|---|
| `PR #N をマージしました。` | 完了 | 修正側を[ポーク](#2-相手を起こすポーク)で起こし（`prompt`: 「PR #<PR 番号> がマージされた。dev-workflow の retro-closeout スキルを実行せよ。」）、購読とチェックインを消して終わる。アーカイブはしない（→ [`retro-closeout`](../retro-closeout/SKILL.md)） |
| `CI red。マージしません。` | ゲート失敗 | 下の「CI が赤だったとき」へ |
| `タイムアウトしました` | 判定不能 | まず `mergeable_state` を見る。`dirty` なら（待っている間に main が動いて衝突した）コンフリクトとして下の「CI が赤だったとき」へ。そうでなければ **1 回だけ**再実行する。2 回続いたら PR 本体に `[レビュー] CI 判定不能` と書き、`ready-for-human` を付けて人へ渡す |
| マージ時に `Pull Request is not mergeable`（HTTP `405`） | マージコンフリクト | 下の「CI が赤だったとき」と同じ手順で修正側へ返す（スレッドには「コンフリクト」と書く） |
| マージ時に HTTP `409`（`Head branch was modified`） | 合意した後に head が変わった（修正側の push など） | **PR を取り直し、head SHA を、スクリプトを起動した時点の head（＝全スレッドを resolve して ready 化したときの SHA。起動前に控えておく）と比べる。** 変わっていれば、増えたコミットは誰もレビューしていないので、**自分で draft に戻し**、増えた差分を読む。**問題があれば**スレッドを立てて往復に戻る（→ レビュー側の[手順 2](#2-指摘を-1-件-1-スレッドで投稿する) → [ラウンドを閉じる](#ラウンドの閉じ方両側共通)）。**問題が無ければ**本手順 7 をやり直す。人には渡さない。head が変わっていない 409 は、下の「それ以外」と同じく人へ渡す |
| それ以外（API 失敗等） | スクリプトが途中で止まった | 内容を PR 本体に `[レビュー]` で書き、`ready-for-human` を付けて人へ渡す |
| ツール結果が `Permission for this action was denied by the Claude Code auto mode classifier` | **スクリプトは起動していない**（権限判定で拒否された。HTTP の 403 とは別物） | 単独呼び出しでなかったなら、単独にして **1 回だけ**やり直す。それでも拒否されたら、`update_pull_request` や merge API での迂回はしない（同じ操作を別の道具で行うことになる）。PR 本体に `[レビュー] マージ手順が権限判定で拒否された` と拒否文の `Reason:` を書き、`ready-for-human` を付けて人へ渡す。PR は draft のまま、購読とチェックインは落とす |

**CI が赤だったとき（コンフリクトも同じ）:**

**直すのは修正側**（→ [修正側の手順 4](#4-ci-赤マージコンフリクトを自分で直す)）。レビュー側はゲートを閉じて知らせるだけ。

1. **レビュー側が自分で PR を draft に戻す**（`mcp__github__update_pull_request(draft=true)`）。CI 側に「失敗時に draft へ戻す」ジョブがあっても、トークンの権限不足で戻らないことがある。直っていれば二重に戻すことになるが無害。**draft に戻さないと、修正の push 後に再 ready 化しても CI が回らない**（push では再実行されず、draft → ready の遷移でしか走り直さない。対象リポの `docs/agents/review-dialogue.md`「CI が走る条件」）。
2. CI の失敗を**指摘として**投稿する —— 失敗が指すファイルに `subjectType="FILE"` のスレッドを立て、落ちたジョブ名と失敗箇所を書く（コンフリクトなら衝突しているファイルに立てる）。修正側が先に起きて PR 本体に `[修正] CI 赤への対応` / `[修正] コンフリクト解消` を書いていても立てる（修正側はそのスレッドに対応済みの commit を返信する。往復は常にスレッドで閉じる）（→ [手順 2](#2-指摘を-1-件-1-スレッドで投稿する)）。指摘はスレッドとして存在することが条件なので、PR 本体コメントにはしない。
3. [ラウンドを閉じる](#ラウンドの閉じ方両側共通)。以降は通常の往復に戻り、全スレッドが resolved になったら本手順 7 をやり直す。修正側の返信が「基盤の問題（コードは直していない）」なら、それが妥当かをログで確かめて resolve し、**1 回だけ**本手順 7 をやり直す。同じ形で 2 回続いたら [8](#8-決裂--打ち切り--人へ渡す) と同じ形で人へ渡す。

**購読とチェックインはマージを確認してから落とす。** ready にした直後に落とすと、赤で往復に戻ったときに相手の応答で起きられない。

- **ready 化・マージに進めるのはレビュー側だけ。** 修正側はどちらも行わない。draft 状態がマージゲート（required status check を設定できないリポでは唯一のゲート）で、合意を判定した側だけがゲートを開けることで第三者性を保つ。
- **CI の緑は ready の条件にしない。** 対象リポの CI は ready 化（と opened）でしか回らない設定が多い（`docs/agents/review-dialogue.md` の `## CI が走る条件`）。**ready 後の push では再実行されない**ので、緑はマージの条件であって ready の条件ではない。`ready_wait_merge.sh` が ready 化のあとに待つ。
- **購読とチェックインを落とす前に、そもそも[ラウンドの閉じ方 4](#4-購読してターンを終える)で購読していたかを一度確認する。** 呼んでいなければ『購読解除』は実質何もしない操作になる（未購読 PR への `unsubscribe_pr_activity` の挙動は未実測）。

### 8. 決裂 / 打ち切り —— 人へ渡す

終わり方は 3 つあり、**人が次に取る行動が違うので書き分ける**。

- **決裂**: 3 往復しても割れたままのスレッドが残った。**論点が対立している**ので、人は中身を裁定する。
- **打ち切り**: 相手が来ない（→ [相手が来ないとき](#相手が来ないとき)）。**対立ではなく往復が成立していない**ので、人は修正側が生きているかを見る。
- **オーナー判断待ち**: 7-1 の表に無い中身の判断（issue がオーナー判断とした golden の差分・受け入れ条件の未達など）が要る（→ [7-1](#7-1-オーナーマージ対象かを判定する)）。**対立でも不在でもない**ので、人は中身を判断し、レビューを払い出し直す。サマリは `[レビュー] オーナー判断待ち` として**何を判断してほしいか**を書く。

どれも手順は同じ:

1. PR 本体にサマリを 1 本。**決裂**なら `[レビュー] 決裂` として**どのスレッドが何で割れているか**、**打ち切り**なら `[レビュー] 打ち切り` として**どのスレッドに応答が無いか**を書く
2. **打ち切りのときは、起床がどこで切れたかを 3 点とも書く** —— 相手を引けたか／ポークを張れたか／`last_run` が何だったか。これが無いと、人は「相手が死んでいる」のか「そもそも相手を引けていなかった」のか区別できない
3. PR に `ready-for-human` ラベル
4. **セッションの応答にも書いて終わる**（オーナーはセッションを開いて読む）
5. **PR は draft のまま**。ready にしない
6. **購読を解除し、保留中のチェックインを消す**（合意側と同じ。解除の前に、そもそも[購読していたか](#4-購読してターンを終える)を確かめる。打ち切りは相手が来ないケースで、未購読が原因になりやすい終わり方なので特に要る）

## 修正側の手順

### 1. head が `claude/issue-<番号>` の PR を作ったら、まずレビューを自分で払い出す

**head が `claude/issue-<番号>` の PR を作ったセッション**（`tdd` / `diagnosing-bugs` / `grill-with-docs` 等。`create-ccw-session` で払い出された子は `outcome_branch` でこのブランチに push するので必ず該当する）は、draft PR を作成した直後に、自分自身で review-dialogue セッションを払い出す（手順は [`create-ccw-session`](../create-ccw-session/SKILL.md)「PR 作成後の自動レビュー払い出し」。プラグインの hook が PR 作成直後にこれを思い出させる）。

**それ以外の修正側はこの手順を飛ばす** —— head が `claude/issue-<番号>` でないセッション（ふつうの直接作業）はレビューを自分で払い出さない。線は prompt ではなく head ブランチで引く（`create_session` は `/` で始まる prompt を拒むので、prompt の文面は当てにならない）。レビューは引き続きオーナーが `/create-ccw-session #NNN review-dialogue` で別途払い出す。

### 2. PR を作ったら必ず自己チェックインを張る

**「レビューが払い出されたら張る」はトリガーが存在しない条件だった。** 払い出すのは親セッションで、[払い出したあと](../create-ccw-session/SKILL.md#払い出したあと)が定めるとおり**親は払い出した子の往復を監視しない**ので、修正側はレビューが払い出されたことを自分では観測できない（手順 1 で自分がレビューを払い出した場合も、レビュー側がいつ動き出すかは観測できない点は同じ）。

したがって、**PR を作ったら、レビューの有無によらず必ず**[ラウンドの閉じ方](#ラウンドの閉じ方両側共通)を実行してからターンを終える。まだレビュー側が居なければ「ラウンドの閉じ方」の手順 1（相手を引く）で相手を引けないので、ポークは飛ばして自己チェックインと購読だけ張る。

### 3. 指摘に応える

起床したら `[レビュー]` マーカーの付いたスレッドを読み、**1 件ずつ**次のどちらかを行う。

- **直す**: 修正して push し、そのスレッドに `[修正] <何をどう直したか>` と返信する。どの指摘に対する修正かを辿れるようにするため、**必ずそのスレッドに返信する**（PR 本体コメントに書かない）。
- **反論する**: `[修正] <なぜこの指摘が当たらないか>` と返信する。**事実**（テストの出力、該当コードの不在、仕様書の該当箇所）を添えられるなら添える。事実を示せればレビュー側は取り下げる。

```
mcp__github__add_reply_to_pull_request_comment(owner, repo, pullNumber, commentId, body)
```

`commentId` は**数値の comment ID**（`#discussion_r...` アンカーの番号）。resolve に使う `PRRT_...` の node ID とは別物。

**PR 本文に書いた内容が変わる修正（方針を変える・対象を広げる／狭める）を push したら、修正側が `mcp__github__update_pull_request(body=...)` で本文を差分に合わせる。** 本文が古いまま残ると、マージ後の履歴が最終の差分と食い違う。

返信と push が済んだら、**閉じ忘れない**: [手順 5 ラウンドを閉じる](#5-ラウンドを閉じる)へ進む（相手を引く → ポーク → 自己チェックイン → 購読）。**修正側は resolve しない**（[手順 7](#7-やらないこと)）。

### 4. CI 赤・マージコンフリクトを自分で直す

**CI が赤になった、またはコンフリクトが出たら、修正側が自分で判断して直す。** レビュー側のスレッドを待たない —— PR activity の CI 失敗通知・コンフリクト通知で起きたら、その場で取りかかる。レビュー側は push しないので、待っても誰も直さない。**ただし PR が ready（draft でない）の間は push しない**（次の段落）。

**前提:** CI は push では再実行されず、draft → ready の遷移でしか走り直さないのが普通（対象リポの `docs/agents/review-dialogue.md`「CI が走る条件」）。ready 化はレビュー側だけが行う。ただし**赤のまま ready に残っていたら、修正側が draft に戻してよい**（`update_pull_request(draft=true)`。ゲートを閉じる方向の操作なので）。CI 側の「失敗時に draft へ戻す」ジョブは、トークンの権限不足で戻せないことがある。

**PR が ready（draft でない）の間は push しない。直すのは draft に戻ってから。** 修正側には、レビュー側がいまマージを試みているかが見えないので、見える状態（draft かどうか）で決める。ready の間に push すると head が変わり、レビュー側のマージが 409（`Head branch was modified`）で止まる。push で CI が走り直さないリポでは、取り込み後の head は CI も通っていない（走り直すリポでも、`ready_wait_merge.sh` が待っていた run とは別の head になる）。ready のままコンフリクトに気づいたら、直さずに待つ。**ただし、レビュー側が動いていない ready（7-2a の `--no-merge` で CI green のまま止まりオーナーのマージ待ち、など）なら待っても誰も動かない**。push せず、PR 本体に `[修正] コンフリクト（ready のため push せず）` と書き、`ready-for-human` を付けて人へ渡す。CI を待っている間に main が動いて衝突した場合は、マージ時の 405 でレビュー側が draft に戻してスレッドで返す（→ 7-2b の表）。上の「赤のまま ready に残っていたら draft に戻してよい」は、戻したあとなら push してよい、という意味でそのまま残る。

**CI が赤のとき:**

1. **ログを読む。** `mcp__github__actions_list` で head SHA の run を引き、`mcp__github__get_job_logs` で失敗したジョブのログを読む。落ちたステップと最初のエラー行を押さえる。推測で直さない。
2. **原因を 3 つに切り分ける。**

   | 区分 | 見分け方 | やること |
   |---|---|---|
   | この PR が原因 | PR ブランチの手元で同じコマンドを流すと再現する | 根本原因を直す |
   | base（main）が原因 | `origin/main` の手元でも同じ失敗が出る。差分が触っていないファイルで落ちている | main に修正が入っていれば `git merge origin/main` で取り込む。無ければこの PR を広げず、CI 赤のスレッド（無ければ PR 本体）に失敗箇所・main で再現する証拠・提案パッチを書き、`ready-for-human` を付けて人へ渡す（回し直しても同じ赤になるだけなので、往復に戻さない） |
   | CI 基盤の問題 | ランナー起動前・checkout や依存導入の途中で落ちた、Actions の課金枠切れなど、テスト本体まで届いていない | コードは触らない。区分と根拠を書き、レビュー側に**1 回だけ**回し直してもらう |

   「flake」は原因ではない。テスト本体まで進んで落ちたなら、まずこの PR が原因として再現を試みる（`-n 0` や対象テスト単体でも流す）。
3. **直す。** テストを skip・xfail・削除して緑にしない。閾値を緩めたり、`# type: ignore` / `# noqa` で黙らせたりもしない。直す範囲は失敗に必要な分だけ。失敗を手元で再現し、直したあと同じコマンドが通ることを確かめる。

**コンフリクトのとき:**

1. `git fetch origin main && git merge origin/main` で取り込む。**rebase・amend・force-push はしない**（レビュー側が同じブランチを checkout していることがある）。
2. 両側の変更の意図を読み、両方を生かす形に解く。lockfile・生成物は手で直さず、生成手順で作り直す。
3. どちらを取っても片方の振る舞いが失われる衝突だけは、解かずに PR 本体へ `[修正] コンフリクト判断要` として両側の意図と選択肢を書き、`ready-for-human` を付けて人へ渡す。

**直したら（両方共通）:**

- 直した内容で PR 本文に書いたことが変わるなら、本文も差分に合わせる（→ [手順 3](#3-指摘に応える)）。
- push の前に、CI と同じコマンドを手元で全部流す（→ [手順 9](#9-push-の前に)）。赤い push を 1 回すると往復が丸 1 周増える。
- レビュー側の CI 赤／コンフリクトのスレッドがあればそこへ `[修正] <区分>: <何をどう直したか（commit）>` と返信し、まだ無ければ PR 本体に `[修正] CI 赤への対応` / `[修正] コンフリクト解消` と書く。そのうえでラウンドを閉じる。
- レビュー側がいない PR（オーナーの直接セッションでレビューを払い出していない）なら、セッションの応答でオーナーに「直して push した。CI を回し直すには draft → ready が要る」と伝える。修正側は ready にしない。
- CI を回すためだけの空 commit や、PR の close → reopen はしない。

### 5. ラウンドを閉じる

→ [ラウンドの閉じ方](#ラウンドの閉じ方両側共通)

**修正側の購読（[ラウンドの閉じ方 4](#4-購読してターンを終える)）を「飛ばしたら分かる」形にしていないのは意図的。** 修正側は PR 作成でハーネスの自動購読が発火するため、この手順で明示に呼ぶのを飛ばしても未購読のままにはならない。『飛ばしたら分かる』歯止めが要るのは、自動購読を持たないレビュー側（手順 4・手順 7・手順 8）だけである。

### 6. チェックインを使い切っても thread が 0 なら人へ渡す

自己チェックインで起きるたびに PR の review thread 数を見る。**指摘スレッドが 1 件も無いまま、チェックインのラダーを 4 回（5 → 10 → 20 → 40 分）使い切って**起きたら、レビュー側が来ていない（払い出し忘れ、または払い出された子が動いていない）とみなし、レビュー側の[「決裂 / 打ち切り —— 人へ渡す」](#8-決裂--打ち切り--人へ渡す)と同じ形で人へ渡す（PR 本体に `[修正] 打ち切り` としてサマリ、`ready-for-human` ラベル、購読解除、保留中のチェックインを消す）。レビュー側の「打ち切り」（[相手が来ないとき](#相手が来ないとき)、チェックインを使い切っても相手が来ない）と鏡像の判定なので、上限をレビュー側と同じ回数に揃える。3 回（5 → 10 → 20 ＝ 35 分）にしないのは、同じ理由でこの短さを退けているため（[判断 0002](https://github.com/hayato1980/claude-skills/blob/main/docs/decisions/0002-review-rounds-wake-the-counterpart-directly.md)） —— 修正側が待つ相手は起動・clone・上流 2 軸レビュー（sub-agent 2 本）まで走るレビュー側で、35 分は正常に働いている相手を切る長さになりえる。

### 7. やらないこと

- **resolve しない。** スレッドを閉じるのはレビュー側。
- **ready にしない・マージしない。** draft を外すのもマージするのもレビュー側。
- **`needs-owner-merge` を外さない。** 付けるときはレビュー側と同じ基準表で判定する（→ [レビュー側の手順 7-1](#7-1-オーナーマージ対象かを判定する)）。外すのはオーナーだけ。
- **レビュー側が維持した指摘に食い下がらない。** 維持されたら従って直す。

### 8. マージされたら retro を回して締める

→ [`retro-closeout`](../retro-closeout/SKILL.md)

### 9. push の前に

**往復中の push には CI が走らない**（対象リポの CI が ready 化でしか回らない場合）。手元で回してから push する。流すコマンドは対象リポの `docs/agents/review-dialogue.md` の `## push 前に流すコマンド`。無ければ、CI の設定ファイルから同じコマンドを拾って流す。

## 環境の前提（実測状況）

公開ドキュメントに記載が無く、実測でしか埋まらない点。**追加で分かったらこの節を書き換えること。**

出典は、この機構を使った往復の実測（日付つき）。

| # | 前提 | 状況 |
|---|---|---|
| 1 | `create_trigger(persistent_session_id, run_once_at)` は相手セッションに届くか | **届く。** `last_run: SUCCEEDED`、発火 `session_id` の suffix がバインド先と一致、相手が実際に行動した。**本番の往復でも届いた** —— レビュー側が R1 を投稿して張ったポークが 15:33:58 に発火し、修正側が起床した |
| 2 | `fire_trigger` による即時発火は届くか | **届かない。** 発火 `session_id` がバインド先と不一致、`last_run` は記録されず、5 分待っても相手は動かなかった |
| 3 | 起こされた相手は `mcp__github__*` を保つか | **保つ。** ポークで起きた子が `issue_read` に成功した |
| 4 | `run_once_at` はどこまで短く置けるか／実発火はいつか | **2 分後でも受理される**（`cron_expression` の「最短 1 時間」は掛からない）。**実発火の遅れは最大 60 秒、実測は 15〜59 秒**（n=5: 59 秒 ／ 15・16・29・53 秒）。**「約 60 秒」ではない** —— 中心値は 60 秒よりかなり小さい。実効遅延 ＝ 設定オフセット ＋ 最大 60 秒 |
| 5 | 同じ PR を 2 セッションが購読でき、**両方にイベントが配信される**か | **登録は両方通る。封筒の到達は両方向で確認した** —— 初回の往復では「修正側 → レビュー側」のみ、2 回目の往復では**逆向き（レビュー側 → 修正側）の封筒も届いた**。ただし**封筒が起床させたのかは切り分けられていない**（下記）。**起床はポークで持ち、この配信には依存しない** |
| 6 | 払い出された子が `subscribe_pr_activity` / `send_later` を持つか | **持つ**（`PushNotification` も） |
| 7 | 子に親と同じ PR 関連のハーネスルールが入るか | **入る**（`<wake reason="external-event">` 封筒、CI 赤時の扱い、自己チェックインの再武装まで同一） |
| 8 | リモートセッションの生存時間 | **未確定。** ただし**消えたことは検出できる** —— 相手にバインドした Routine が `ended_reason: auto_disabled_session_gone` を残す（実例あり）。なお `last_run: FAILED` 単独が何を意味するかは**未実測** |
| 9 | ハーネス直結の peer messaging（`ListAgents` / `SendMessage`）は兄弟セッションに届くか | **届かない。** 兄弟が 6 本 RUNNING でも `ListAgents` は 0 件を返す（CCW は 1 セッション 1 コンテナ） |
| 10 | `list_sessions` は何件まで一度に引けるか | **API の上限 100 件まで、1 回で引ける。** 1 セッションあたり約 2.7KB（`session_context` / `external_metadata` / `usage` が全部乗る）なので、20 件（52,123 文字）でもツール結果の上限を超える。ただし超えた結果は弾かれず、ツールが**ファイルに保存する**。`limit=100` で 272,928 文字のファイルになり、`jq` で問題なく読めた（2026-10-18）。以前は `limit=30` の応答 58,833 文字が弾かれたため 20 件に絞っていた。読み方は [手順 1](#1-相手を引く) |
| 11 | レビュー側（CCW の子）から `ready_wait_merge.sh` でマージまで通るか（`GH_TOKEN` が届くか、agent proxy が REST の merge を通すか） | **通る（green 経路で n=1）。** `GH_TOKEN` / `GITHUB_TOKEN` は CCW セッションに届いている（2026-10-12 に確認）。ある PR で、レビュー側の子が全スレッド resolve 後に `ready_wait_merge.sh` を実行し、**ready 化は proxy が GraphQL を 403 で止めたため REST shim（`ccr/ready_for_review`）へフォールバックして成功、CI green を待って `PUT /pulls/{n}/merge` も proxy を通ってマージされた**（resolve 03:32:24 → ready 03:32:39 → merge 03:36:16 UTC）。**未実走**: GraphQL がそのまま通る経路、CI 赤でレビュー側が draft に戻す経路。**ただし起動そのものが止まることがある**: 別の PR ではレビュー側の子（auto mode）が `git checkout … && git pull … && bash scripts/ci/ready_wait_merge.sh 1503` を叩き、ツール権限判定で拒否された（transcript の `tool_result_meta` が `non_execution_kind: automode-blocked` / `reason_type: classifier` / `decision: reject`。スクリプト内の HTTP 403 ではない）。その後オーナーが `/ready-merge` と打つと、同じ素の Bash 呼び出しが分類器を通ってマージまで進んだ。分類器は、ユーザーが明示的に頼んだかどうかで判定を変える。そのため、通る回と止まる回があった。直接セッションでも、PR の無いブランチで引数なしに叩くだけで `[Merge Without Review]` として拒否されることを再現した（2026-10-13）。既存の `Bash(bash scripts/db/psql_ro.sh*)` に一致する単独呼び出しも `reason_type: classifier` になった。公式ドキュメントのとおり、`bash …*` の許可ルールは auto mode では無効になる。対策は、インタプリタを前置しない許可ルール `Bash(scripts/ci/ready_wait_merge.sh*)` を置き、手順 7-2b でスクリプトを直接・単独で叩くこと。`autoMode` の散文ルールはプロジェクトの settings からは読まれないので、この用途には使えない |

**`create_trigger` が出す MCP connector 警告は、既存セッションへの差し込みには当てはまらない。** 文面は「この Routine が fire する**セッション**が connector ツール無しで走る」だが、これは**新規セッションを作る発火**の話で、前提 3 のとおりポークで起きた相手は `mcp__github__*` を保っている。

**2 回目の往復で分かったのは「封筒は届く」までで、「封筒が起こす」ではない。** 修正側が R1 に着手したとき手元にあった通知は 11 件すべて GitHub の封筒（`pull_request_review.submitted` ＋ `pull_request_review_comment.created` × 10、`current-time` 15:30:36–15:30:37Z）で、**ポークは含まれていなかった**（レビュー側の R1 ポークは 15:33:58 発火で、次のバッチに現れた）。一方、修正側の最初の返信は 15:36:29 で、**ポーク発火の 2 分 31 秒後**でもある。封筒が idle のセッションを起こしたのか、ポークで起きたときにキューが流れたのかは、**受け取った側のログからは区別できない**。初回の「未達」を「届く」に書き換えるのはこの節で最も重い更新なので、確認できた範囲（＝封筒の到達）までしか書かない。

**「往復が黙って死んだ」実例は観測されていない。** 初回の往復で人が介入したのは**チェックインが焚かれなかったから**ではなく、**60 分の粒度が往復のテンポ（1 ラウンド数分〜十数分）に対して遅すぎ、人間が先に気づいたから**である。機構は壊れておらず、粒度が間違っていた。

**「同一アカウントのエコーとして落とされた」という説明は成り立たない。** レビュー側は自分が投稿した直後、**自分自身の投稿のエコーを 8 件すべて wake として受け取っている**（購読開始 1 件・レビュー本体 1 件・指摘コメント 6 件）。封筒の段階での抑止は 1 件も掛かっておらず、落としたのはハーネスではなく本文の役割マーカーを読んだレビュー側の判断だった。

**ポークが届かなくなったら、チェックインが往復を運ぶ。** 遅くなるだけで人手には戻らない。逆に**チェックインまで焚かれなくなったら**、レビュー側を常駐させず往復のたびにオーナーが `review-dialogue` を再度払い出す逐次型に落とす。差分の基準点は毎回 merge-base なので、文脈を失っても読み直せる。
